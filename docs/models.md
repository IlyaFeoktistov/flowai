# Модели

flowAI использует локальные нейронные сети (LLM) через Ollama — либо через
обычный Ollama-путь, либо через собственный форк `llama.cpp` с
expert-streaming (см. ниже). Ни одна модель не уходит во внешний API.

## Где что настроено

- `src/settings.py` — runtime-настройки, персистятся в SQLite
  (`~/.local/share/flowai/flowai.db`, таблица `settings`, key/value JSON).
  Дефолты читаются из переменных окружения при первом запуске, дальше
  сохранённое значение из БД побеждает (кроме `debug` — см. комментарий в
  файле). Меняются через `/settings` в UI.
- `src/mcp_agent/model_config.py` — константы для самого движка (лимиты
  self-heal, тайминги, sampling: temperature/top_p/top_k/repeat_penalty,
  бюджеты шагов графа по ролям пайплайна). Читаются один раз при импорте,
  не runtime-переключаемые (кроме `num_ctx`, дублирующего
  `settings.get("num_ctx")` — см. ниже почему).
- `src/expert_streaming.py` — обёртка над форкнутым `llama.cpp`-бинарником
  (`vendor/llama-expert-streaming`) с настоящим per-token expert offloading
  для MoE-моделей.
- `src/ui/tui/settings.py` — `_ITEMS` (список пунктов `/settings`); выбор
  модели показывает только установленные (`ollama list`) с размером весов.
- `src/model_params.py` — параметры генерации отдельно для каждой модели
  (см. «Параметры модели» ниже).

## Дефолтная модель

`chat_model` (`settings.py`) по умолчанию — `glm-4.7-flash:q4_K_M`: MoE,
~3B активных параметров, 17.7 GB весов. Выбрана вместо `qwen3-coder:30b`
(~18 GB весов, тоже MoE, ~3.3B активных) за заметно лучшую скорость на
этом железе при близком весе (характеристики железа, на котором всё
здесь замерено — см. корневой `README.md`, раздел «Что умеет» →
«Ограничения»: NVIDIA RTX 4050 Laptop, 6 GB VRAM, 16-ядерный CPU,
32 GB RAM).

**Требует `expert_streaming_enabled=ВКЛ`** (дефолт с 2026-08-14) — обычный
Ollama-путь не поддерживает архитектуру `glm4moelite` без патча форка.
Если бинарник не собран, `agent_builder` тихо откатывается на обычный
Ollama-путь — с той же моделью это не сработает, `/settings` придётся
переключить на другую (`qwen3-coder:30b` работает и на голом Ollama).

`qwen3-coder:30b` — полностью рабочая альтернатива на голом Ollama-пути
(без сборки форка), если `expert_streaming_enabled` выключен. Работает в
основном на CPU на этой машине (6 GB VRAM, см. характеристики выше)
— `ollama ps` показывает ~79%/21% CPU/GPU.

## expert_streaming — зачем отдельный бэкенд

Ollama всегда использует статичный CPU/GPU-сплит весов MoE-модели,
решённый один раз при загрузке. Форк `llama-expert-streaming`
(`vendor/llama-expert-streaming`, собирается `setup.py`'s
`expert-streaming` шагом) добавляет `-ehs` — динамический per-token
expert offloading: какие эксперты держать «горячими» в VRAM решается на
каждом токене, а не один раз при загрузке.

Trade-off (см. докстринг `expert_streaming.py` и живые замеры там же):
prompt-processing может упасть в разы, генерация в среднем ускоряется
на треть — это компромисс, не безусловное ускорение. Это чужой
недособранный community-PR без гарантий совместимости с будущими
версиями `llama.cpp` — поэтому дефолт ВКЛ только для `glm-4.7-flash`
(для которой это обязательное условие работы вообще), а не для любой
модели по умолчанию.

`expert_streaming.ensure_running()` возвращает `(False, reason)` вместо
исключения при сбое — падение сборки/бинарника не роняет чат, просто
откатывает на обычный Ollama-путь с той же моделью (которая может не
поддерживаться на этом пути — см. выше).

Процесс `llama-server` **не останавливается при выходе из flowai** — модель
остаётся загруженной, следующий запуск (или параллельный второй `flowai`/
веб) подхватывает его через `~/.local/share/flowai/expert_streaming_server.json`
вместо многоминутной перезагрузки. Если конфиг изменился (другая модель,
`num_ctx`, thinking) — старый сервер убивается и поднимается новый.
Выгрузить вручную — `/instances` (или «Инстансы» в вебе).

## Загрузка модели

Перед ходом `agent_builder.preload_chat_model` грузит чат-модель заранее и
шлёт события `model_loading`/`model_loaded`: в CLI — фраза спиннера
«загружаю модель … ~42%», в вебе — подпись в футере хода. Процент есть
только у llama.cpp — оценка по реально прочитанным байтам
(`expert_streaming._load_progress`: RSS mmap-части + `rchar` заливки на GPU
относительно размера блоба); Ollama прогресс загрузки не отдаёт, там только
«загружаю…» и время.

Флаг сервера `--reasoning` следует только `show_thinking`; thinking
конкретного вызова (судья, голос) выключается per-request через
`chat_template_kwargs.enable_thinking` — поэтому сборка основной модели и
судьи больше не перезапускает `llama-server`.

## /instances — что загружено сейчас

`src/instances.py` опрашивает оба бэкенда: Ollama (`/api/ps` — RAM/VRAM на
модель) и наш llama.cpp-форк (RSS процесса; VRAM — по-процессно из
`nvidia-smi`, а где он этого не отдаёт, как под WSL2, — оценкой «занято на
GPU минус Ollama», помечено `~`). Выгрузка: Ollama — `keep_alive=0`,
llama.cpp — остановка процесса. После выгрузки собранные агенты
сбрасываются, следующий ход загрузит модель заново.

## OLLAMA_NUM_CTX и почему "влезает" — не вопрос размера весов

Агент всегда грузит модели с контекстным окном `settings.get("num_ctx")`
(дефолт 30000, синхронизирован вручную с
`model_config.OLLAMA_NUM_CTX` — см. комментарии в обоих файлах про то,
почему не общий импорт). KV-cache при этом окне — это несколько GB
ПОВЕРХ весов модели, а не мелочь: часто именно он выталкивает модель,
которая «должна» влезать по размеру весов, в частичный CPU-offload.

**Нет формулы "веса < VRAM → влезает"** — единственный надёжный способ
узнать реальный сплит — живой замер: `ollama ps` сразу после настоящего
запроса, или `/instances` (RAM/VRAM каждой загруженной модели по обоим
бэкендам).

## Параметры модели

`/settings` → «параметры модели» (в вебе — секция «Параметры модели» в
настройках): `temperature`, `top_p`, `top_k`, `min_p`, `repeat_penalty`,
`repeat_last_n`, `num_predict`, `num_ctx` — **у каждой модели свои**
(`m` — выбрать другую модель, `r` — сбросить параметр). Значение
собирается в три слоя (`model_params.py`): общие дефолты (бывшие
константы `model_config.py`) ← дефолты семейства модели (сейчас только
`glm-4.7-flash`: `temperature=0.7, top_p=0.95, min_p=0.01,
repeat_penalty=1.0`) ← то, что задал пользователь. Хранится в ключе
`model_params` таблицы `settings`. Глобальный `num_ctx` остаётся дефолтом
окна для моделей без своего значения. Изменение применяется со следующего
вызова модели (собранные агенты сбрасываются); смена `num_ctx` на
expert-streaming перезапускает `llama-server`.

`no_mmap` (ВКЛ/ВЫКЛ, по умолчанию ВЫКЛ, Enter переключает; только для
llama.cpp-форка, на Ollama не влияет) — запуск `llama-server` с
`--no-mmap --direct-io`. На `glm-4.7-flash` ускоряет обработку промпта
примерно на 46% (198 → 289 tok/s, генерация та же), но весь GGUF (19 ГБ)
ложится в память, которую ядро не может вытеснить: вместе с IDE это
роняет WSL на 24 ГБ по OOM. С ВЫКЛ веса остаются в mmap — вытесняемом
файловом кэше. Смена перезапускает `llama-server`.

Семейные дефолты — связка, проверенная только целиком, поэтому на пути
без тулов (casual-ответ) они не применяются; значения пользователя
применяются всегда.

`num_ctx` понижен с 65536 до 30000 не из-за риска переполнения (65536
был безопасен на этой машине, см. характеристики выше, по расчёту в
`model_config.py`), а потому
что на 65536 `expert_streaming`'s autofit не находил ни одного
hot-slot для экспертов ни при f16, ни при q8_0 KV-cache — на 30000
находил 10.

## Сжатие истории

- **Между ходами** (`compress.py:compress_history`, и в CLI, и в вебе):
  когда последний вызов модели заполнил окно больше чем на `compress_at`
  (дефолт 0.70) от `num_ctx`, всё, кроме последних 6 сообщений,
  сворачивается в одно резюме (пишет та же чат-модель через
  `_build_chat_model` — тот же бэкенд, без второй копии модели). Полная
  история остаётся в episodic. Прежний `context_limit` убран: порог
  считался от суммы `tokens_in` за ход и от числа, не совпадавшего с
  `num_ctx`.
- **Внутри хода**: `_CompactResearchMiddleware` (`mcp_agent/compaction.py`)
  сворачивает старые результаты тулов в дайджест при приближении к лимиту.
  Если модель всё же вернула «контекст переполнен», `stage_runner.py:
  _shrink_for_overflow` сначала сворачивает предыдущий диалог в резюме,
  а при повторном переполнении отбрасывает его и обрезает текущий запрос
  до 8000 символов — ход продолжается, обычные попытки на это не тратятся.

## Другие модели в системе

- `vision_model` (дефолт `llava:13b`) — `analyze_image`.
- `stt_model` (дефолт `medium`, faster-whisper) — голосовой ввод (Alt+R).
- `voice_chat_model` (дефолт `qwen3:8b`) — чат-модель, на которую
  `settings.py:set_value` автоматически переключает `chat_model` при
  включении `voice_mode` (и возвращает обратно при выключении — прежняя
  модель запоминается в памяти процесса, не персистентно).
- `image_gen_model` (дефолт `stabilityai/sdxl-turbo`) — `generate_image`/
  `edit_image`, устройство берётся автоматически (`cuda`, если детектится
  GPU через torch или `nvidia-smi`, иначе `cpu`).
- TTS (Chatterbox) и MusicGen (`facebook/musicgen-small`) не настраиваются
  через `chat_model`-механизм — свои отдельные модели, CPU по умолчанию
  (см. [generative-features.md](generative-features.md)).

## Переключение модели

Через `/settings` в UI (runtime, персистится сразу в SQLite) — не через
`.env`/`OLLAMA_MODEL`: та переменная только сеет `_state`-словарь при
самом первом запуске на чистой установке (нет строки в БД). Как только
запись в `settings`-таблице появилась — что случается сразу при первом
касании `/settings`, или сразу же у любого, у кого уже есть
`flowai.db` — переменная окружения тихо игнорируется. Для новой
установки дефолт меняется прямо в `settings.py`.

Смена `chat_model`/`num_ctx`/`expert_streaming_enabled` подхватывается
на следующий ход — кеши `agent_builder.py` (`_tools_cache`/
`_agent_cache`/`_role_agent_cache`) держат `chat_model` частью
freshness-ключа (см. [architecture.md](architecture.md)'s BuildCache
раздел).

# 3D-генерация игровых ассетов — статус и план

## Что вообще делаем

Ищем способ генерировать 3D-модели локально (на своей RTX 4050 Laptop, 5.9 ГБ VRAM)
под игровые нужды: меш + качественные текстуры, запечённые на UV-развёртку, + риг + анимации.
Готового решения "всё в одной модели" не существует — собираем пайплайн из нескольких
отдельных инструментов.

Не имеет отношения к самому flowAI-чату (Ollama здесь не используется) — это отдельный
локальный инструмент/сервис, который в перспективе можно обернуть как tool в `tools/`
(по образцу `tools/image_gen.py` + `mcp_agent/servers/image_gen_server.py`), но пока это
чисто эксперимент вне кода flowAI.

## Пайплайн (из чего должен состоять)

1. **Mesh + текстуры** — генеративная модель image/text-to-3D
2. **Ретопология** — сырой меш с генератора слишком плотный для игры, нужно уменьшать полигонаж
3. **Риг** (скелет + скиннинг)
4. **Анимации**

## Что попробовали и с каким результатом

### 1. Mesh + текстуры: Hunyuan3D-2GP

Репозиторий: https://github.com/deepbeepmeep/Hunyuan3D-2GP (low-VRAM форк Hunyuan3D-2.0
с оффлоадингом через `mmgp`).

Развёрнуто в `~/projects/Flowio/hunyuan3d-2gp` (venv на Python 3.11, torch 2.5.1+cu124).

**Что пришлось решить по пути:**
- pip-пакет `nvidia-cuda-nvcc-cu12` (обе версии, 12.4.131 и 12.9.86) не содержит реальный
  бинарник `nvcc` — только `ptxas` и заголовки. Для сборки CUDA-расширений (`custom_rasterizer`,
  `differentiable_renderer`, `diso`) пришлось ставить `nvcc` системно:
  `sudo apt install nvidia-cuda-toolkit`.
- `pip install diso` падает без `--no-build-isolation` (torch не виден в изолированном
  build-окружении).
- Свежий `diffusers` (0.39.0, тянется требованиями репо без пина версии) требует
  `trust_remote_code=True` для кастомного пайплайна `hunyuanpaint`. Пофиксено прямо в клоне:
  `hy3dgen/texgen/utils/multiview_utils.py`, строка с `DiffusionPipeline.from_pretrained(...)`.

**Тестовый прогон** (`test_generate.py` в корне клона, профиль offload = 4, демо-картинка
`assets/demo.png`):

| Этап | Время | Пик VRAM |
|---|---|---|
| Генерация меша (Hunyuan3D-2mini) | 84.6с | 2.2 ГБ |
| Генерация текстуры (Hunyuan3D-Paint) | 318с (~5.3 мин) | 2.2 ГБ |
| **Итого** | **~6.7 мин** | **2.2 ГБ из 6 ГБ** |

Результат в `test_output.glb`:
- Меш: 339 580 вершин / 679 168 граней — плотный, сырой, под игру нужна ретопология.
- Текстура: только `baseColorTexture` 2048×2048 (альбедо), запечённая на UV. Отдельных
  metallicRoughness/normal текстур **нет** — только фиксированный скаляр roughness (~0.9)
  на весь меш.

**Важный вывод**: это веса **Hunyuan3D-2.0**, а не 2.1. Полный многоканальный PBR
(albedo+metallic+roughness+normal), который изначально и был целью, даёт только
Hunyuan3D-**2.1** (модель Hunyuan3D-Paint v2.1). Проверил код и README этого GP-форка —
поддержки 2.1 в нём нет вообще. VRAM с большим запасом (2.2 из 6 ГБ) — есть все шансы,
что профиль 3 (быстрее профиля 4) тоже влезет, не проверяли.

### Внутри "mesh + текстуры" — это не одна модель, а конвейер

Видно по логу прогона (строки `Hooked to model ...` от mmgp). На каждом шаге отдельная
нейросеть (или классический движок), а не единая end-to-end модель:

1. **rembg** (`BackgroundRemover`) — отдельная маленькая модель, вырезает фон с входного
   фото перед подачей дальше.
2. **Hunyuan3D-DiT** (Hunyuan3D-2mini) — diffusion-трансформер, генерирует геометрию
   (voxel/SDF → mesh через marching cubes) по картинке. Плюс свои `ShapeVAE` и
   `SingleImageEncoder` (кодирует картинку в условие для диффузии).
3. **Delight-модель** (`texgen_workerdelight_model*`: VAE + CLIP text encoder + UNet,
   SD-based) — "снимает" освещение/тени с референсного изображения, иначе тени с фото
   впечатались бы прямо в текстуру.
4. **Multiview-модель** (`texgen_workermultiview_model*`, это и есть кастомный пайплайн
   `hunyuanpaint`, из-за которого была ошибка `trust_remote_code`) — тоже SD-based
   diffusion, генерирует несколько согласованных между собой видов объекта с текстурой,
   ориентируясь на геометрию меша.
5. **custom_rasterizer / differentiable_renderer** — уже не нейросеть, а рендер-движок
   (те самые CUDA-расширения, которые собирали руками): проецирует картинки с
   шага 4 на UV-развёртку меша и запекает их в итоговую `baseColorTexture`.

Именно поэтому шаг с текстурой (318с) намного дороже шага с мешем (85с) — на нём
последовательно работают две диффузионные модели (delight + multiview), а не одна.

      **Находки по пути (все на реальном тестовом меше, `e22f11.glb`, меч):**
      1. Официальный `stabilityai/stable-diffusion-2-1` убран с HuggingFace (401/
         Repository Not Found) — как и предупреждал README SuperMat, нужна замена
         `sd2-community/stable-diffusion-2-1`.
      2. `xformers` — жёсткий top-level import в коде SuperMat И в самом `diffusers`
         (`attention_processor.py`), даже когда рантайм-флаг `use_xformers=False` —
         нужен установленный пакет независимо от того, используется ли он реально.
         Версия по умолчанию с PyPI (0.0.35) собрана под torch 2.10+cu128 и падает
         на импорте (`aten::_flash_attention_forward` schema mismatch) против нашего
         torch==2.5.1+cu124 — нужна точная `xformers==0.0.28.post3` (единственная,
         реально собранная под 2.5.1), ставится с `--no-deps`, чтобы не утянуть
         другой torch. `einops` — тоже используется, но отсутствует в requirements.txt
         репозитория вообще (обычный `ModuleNotFoundError`, не конфликт версий).
      3. Присваивание `obj.matrix_world = [список списков]` в Blender **молча
         теряет translation** (поворот применяется, позиция — нет) — нужно
         оборачивать в `mathutils.Matrix(...)`, иначе восстановленные из JSON
         камеры для обратной проекции оказываются все в начале координат
         (воспроизвели: все 15218 граней ошибочно "лучшим видом" считали одну
         и ту же камеру, пока не пофиксили).
      4. Back-projection — per-face "лучший ракурс" по `dot(нормаль, направление
         на камеру)`, БЕЗ raycast-проверки видимости/окклюзии (не реализовывали
         — обычный self-bake через Cycles, restricted per-face selection).
         Известное ограничение: на самозаслоняющих формах возможен лёгкий шов
         между соседними ракурсами — на тестовом мече виден слабый горизонтальный
         шов примерно на середине клинка, но общая связность материала по всей
         модели в порядке. Можно улучшить raycast-проверкой видимости позже, если
         станет заметно мешать.
      5. Итоговая текстура — ОДНА картинка (G=roughness, B=metallic), не два
         отдельных файла: экспортёр glTF в Blender авто-детектит
         `metallicRoughnessTexture` только когда Roughness/Metallic у Principled
         BSDF запитаны от одной картинки через `Separate Color` — с двумя разными
         картинками этот паттерн не распознаётся и текстура тихо не экспортируется
         (тот же принцип уже использовали для AO/`occlusionTexture` выше).
         `project_material_to_uv.py` также сохраняет исходный материал меша
         (albedo/normal/AO из `rebake_texture.py`) и добавляет roughness/metallic
         в НЕГО, а не строит материал с нуля — иначе предыдущие текстуры терялись.

      Проверено сквозным реальным прогоном на `e22f11.glb`: итоговый glTF содержит
      корректный `metallicRoughnessTexture` (G/B с реальной вариацией, не пустые/
      не однотонные) вместе с сохранёнными `baseColorTexture`/`normalTexture`.
- [x] **Ретопология** — сделали, headless Blender 4.0.2 (поставлен через apt в WSL,
      понадобился отдельно `python3-numpy` для системного Python 3.12 — иначе у
      Blender падает встроенный glTF-addon импорта). Скрипт:
      `~/projects/Flowio/hunyuan3d-2gp/retopo.py`.

      **Важная находка**: сырой меш от Hunyuan3D-2mini — это marching-cubes
      экстракция, у него **34 825 несвязных island'ов** (шум/артефакты), из них
      121 остров ≥100 граней (реальные части: тело/плакат/палки/руки, 6 664–47 670
      граней каждый) и 34 704 совсем мелких (< 100 граней, суммарно 96 462 грани —
      почти 15% всех граней это мусор). 339 856 неманифолдных рёбер из ~1 млн.
      Из-за этой фрагментации обычный **Decimate modifier застревал на ~36 200
      гранях** и не сокращался дальше вообще, независимо от целевого ratio —
      алгоритм не может коллапсить topology ниже минимума на каждый island.

      **Решение**: сначала **Voxel Remesh** (пересобирает меш как единую чистую
      watertight-поверхность, игнорируя старую фрагментированную топологию и UV),
      потом Decimate на результате. На тесте (`test_output.glb`, профиль 4,
      voxel_size=0.01): 679 168 → Remesh → 93 094 → Decimate (2 итерации) →
      **15 477 граней** (цель была 15 000, попадание точное). Силуэт визуально
      подтверждён рендером (`render_preview.py`) — пингвин, плакат, обе палки, руки,
      клюв, лапы все на месте, без дырок/развалов. Результат: `test_output_retopo.glb`.

      Побочный эффект Remesh — UV полностью пересобираются, старая
      `baseColorTexture` больше не накладывается (превью без текстуры, серое) —
      это и есть следующий пункт (перезапекание текстур).
- [x] **Перезапекание текстур после ретопологии** — сделали, без StableGen.

      **StableGen отпал**: нужен Blender 4.2-4.5/5.1+ (не проблема после обновления), но
      **только интерактивный UI, никакого headless/scripted режима** — несовместимо с
      целью `/gen_model` как автоматического тула. Плюс отдельный сервис ComfyUI + минимум
      8 ГБ VRAM для SDXL (у нас 6). Вместо AI-регенерации текстуры — перенос уже готовой
      альбедо-текстуры со старого меша на новую UV через Cycles bake
      (`~/projects/Flowio/hunyuan3d-2gp/rebake_texture.py`), Selected-to-Active,
      без AI/диффузии вообще.

      **Три находки по пути**, все важны для будущего `/gen_model`-тула:

      1. **apt-пакет Blender для Ubuntu не подходит** — сначала поставили `sudo apt
         install blender` (4.0.2), понадобился ещё `python3-numpy` для системного Python
         (иначе падает встроенный glTF-addon). Но обычный Decimate/Remesh работал, а вот
         Cycles-бейк (любого типа — DIFFUSE, EMIT, self-bake, selected-to-active,
         с денойзом/без, под Xvfb/без) стабильно давал только альфа-канал, RGB всегда
         ноль. **Перешли на официальную сборку через `snap install blender --classic`**
         (сейчас 5.1.2) — apt-версию удалили.
      2. **`type='DIFFUSE', pass_filter={'COLOR'}` не работает даже на официальном
         Blender 5.1.2** — стабильно даёт нулевой RGB (только альфа), причина не
         выяснена до конца, но воспроизводится железно. Рабочий обход: **bake
         `type='EMIT'`**, с текстурой источника, перенаправленной через Emission-шейдер
         вместо Base Color — с этим и Selected-to-Active, и self-bake дают нормальный
         результат. Также отдельно: если нода-текстура (цель бейка) подключена в Base
         Color *до* бейка — Blender ругается "circular dependency for image X" и всё
         равно даёт чёрный результат; подключать её нужно *после* бейка.
      3. **После Decimate/Remesh меш остаётся flat-shaded** (у каждой грани свой
         normal) — при экспорте в glTF это заставляет экспортёр физически расщеплять
         вершину на каждой грани (нужен один normal на вершину). Результат: меш
         визуально выглядит целым, но топологически развалился на тысячи
         несвязанных островков (на тесте — 15 573 островка на 17 388 граней, почти
         каждая грань отдельно) — именно то, что ты заметил ("вершина отклеивается от
         модели"). Фикс в `retopo.py`: `remove_doubles` (сварка) + `shade_smooth()`
         **перед** экспортом. После фикса — 1 островок, 0 неманифолдных рёбер.
         UV-развёртка (`smart_project` в `rebake_texture.py`) добавляет свои швы
         (143 островка на том же меше) — это нормально и неизбежно для любого
         текстурированного ассета, не баг.

      Финальные скрипты: `retopo.py` (remesh+decimate+weld+smooth),
      `rebake_texture.py` (bake альбедо на новую UV), `render_preview.py` (визуальная
      проверка). Результат: `test_output_retextured.glb`.

## Ctrl+C реально останавливает /gen_model + multi-view (Hunyuan3D-2mv)

- [x] **Реальная остановка `/gen_model` по Ctrl+C** — раньше `Ctrl+C` отменял только
      asyncio-таск (`task.cancel()`), а сам подпроцесс (Blender/Hunyuan3D-2GP/UniRig/
      SuperMat), запущенный блокирующим `subprocess.run()` внутри
      `loop.run_in_executor()`, молча доживал до конца в фоне — тот же класс бага,
      что уже документирован в `ui/music_stream.py` для `/music`. Сделали: новый
      `gen3d/pipeline.py:_run_subprocess()` на `subprocess.Popen` + поллинг
      `proc.poll()` вместо `subprocess.run(timeout=...)`, `cancel_event: threading.Event`
      протянут по всей цепочке (`run_gen_model` → каждый этап), `ui/app.py` дёргает
      зарегистрированный колбэк (`set_gen3d_active`) прямо перед `task.cancel()` в
      `_interrupt`. Проверено реальным прогоном (не только юнит-тестом на `sleep`):
      отмена через ~2с после старта, дочерний Hunyuan3D-2GP процесс реально исчезает
      из `ps aux`, чистый результат без трейсбэка.

      **Найденный по пути отдельный баг (важнее самой фичи)**: первая версия
      `_run_subprocess` использовала `stdout=subprocess.PIPE, stderr=subprocess.PIPE`
      и вычитывала их только один раз в конце через `proc.communicate()` — классический
      Python subprocess deadlock: у pipe маленький фиксированный OS-буфер (~64 КБ на
      Linux), а между вызовами `proc.poll()` никто их не вычитывал. Как только дочерний
      процесс (у Hunyuan3D-2GP только логов загрузки моделей — уже больше 64 КБ) заполнял
      буфер, он блокировался на `write()` — воспроизвели живьём на реальном multi-view
      прогоне: процесс завис в состоянии `S`, `/proc/<pid>/wchan` = `pipe_write`, VRAM/CPU
      почти не менялись 5+ минут. Это был бы баг **во всём пайплайне**, не только в новом
      коде — просто раньше `subprocess.run()` сам вызывал `communicate()` сразу и не
      попадал в эту ловушку. Фикс: stdout/stderr — в `tempfile.TemporaryFile()` (обычный
      файл, а не pipe с фиксированным буфером), вычитываются один раз после того как
      процесс завершился/убит. Перепроверили: синтетический тест на ~4 МБ вывода
      отрабатывает за 0.3с вместо зависания, и реальный multi-view прогон после фикса
      дошёл до конца (см. ниже).

# flowAI

Python CLI AI-ассистент на базе локальных моделей через Ollama. Без внешних API — всё работает на твоей машине: чат с инструментами (агент читает/пишет файлы, гоняет git, ищет в интернете), генерация и редактирование картинок, голосовой ввод/ответ, генерация музыки.

Вся конфигурация в этом репозитории (параметры модели, лимиты контекста, тайминги ретраев, устройство промптов и тулов и так далее) — не взята из общих рекомендаций, а получена эмпирически, на реальных прогонах на реальных задачах. В коде (в основном `mcp_agent/*.py`) это оставлено намеренно как комментарии вида «живой прогон: …» прямо рядом с константой/решением, которое из этого прогона следует — с конкретным багом или наблюдением, который к нему привёл. Если меняешь одну из таких настроек, стоит сначала прочитать комментарий рядом с ней — там объяснено, какую именно проблему она решает и на что был похож живой сбой без неё.

## Что умеет

| Возможность | Как | Описание |
|---|---|---|
| Чат с инструментами | LangGraph-агент + MCP | Читает/пишет файлы, git, bash, поиск в интернете, память о проекте — 30+ тулов |
| Чтение изображений | `analyze_image` (vision-модель) | Описывает картинку, OCR, отвечает на вопрос про неё |
| Генерация изображений | `generate_image` (SDXL/FLUX) | Рисует по текстовому описанию (нужна GPU) |
| Редактирование изображений | `edit_image` (img2img) | Меняет существующую картинку по описанию, сохраняя композицию |
| Голосовой ввод | `Alt+R` (faster-whisper) | Наговорил — текст сам появился в поле ввода |
| Голосовой ответ | голосовой режим (Chatterbox) | Ответ агента озвучивается вслух |
| Генерация музыки | `generate_music` (MusicGen) | Инструментальная музыка/эмбиент по описанию — без вокала |
| Генерация 3D-моделей | `generate_3d_model` (Hunyuan3D-2GP + Blender) | Текстурированная .glb-модель по картинке/описанию, опционально с ригом (нужна GPU + отдельная установка, см. «Генерация 3D-моделей») |
| Анимация 3D-моделей | `animate_3d_model` (Animato) | Оживляет уже риггованную модель по текстовому описанию движения |
| Веб-поиск | SearXNG | Поиск через локальный self-hosted поисковик |
| Чтение веб-страниц | `mcp-server-fetch` | Открывает URL, возвращает чистый текст |
| Память | SQLite | Помнит факты о пользователе и о конкретном проекте между сессиями |
| Многоходовой диалог | — | Помнит контекст разговора, автоматически сжимает при приближении к лимиту |

**Ограничения:**
- Контекстное окно 65536 токенов по умолчанию (настраивается, `OLLAMA_NUM_CTX`; нативно `qwen3-coder:30b` поддерживает до 262144, но на большинстве железа для этого не хватит RAM под KV-cache, см. «Модели») — сжимается автоматически, но очень длинные диалоги всё равно стоит начинать заново
- Генерация/редактирование изображений требует GPU (NVIDIA, от 6 GB VRAM)
- Голосовой ответ (TTS) и генерация музыки — CPU-only, заметно медленнее реального времени (см. раздел «Голосовой режим»)
- На WSL2 голосовой ввод/вывод идёт через мост на `powershell.exe` — на «чистом» Linux этот мост не нужен, но пока не переносился (см. `ui/audio.py`)
- Генерация 3D-моделей и Ollama-чат соревнуются за одну и ту же VRAM: если во время `/gen_model`/`/anim` открыт активный чат, `gen3d/pipeline.py` сам выгружает текущую chat-модель перед тяжёлыми GPU-этапами (она подгрузится заново на следующее сообщение) — но если что-то другое держит VRAM занятой одновременно, возможен `CUDA out of memory` (безопасная, легко читаемая ошибка, не крэш — см. «Генерация 3D-моделей»)

## Установка

Один скрипт ставит всё — основной `.venv`, опциональные генерация/редактирование
картинок, голосовой ввод/ответ и весь `/gen_model`-пайплайн (каждый компонент в
своём venv, версии `torch`/CUDA у них несовместимы друг с другом):

```bash
# Системные пререквизиты (один раз, нужен sudo — скрипт ничего сам не sudo'ит):
sudo apt install python3.12 python3.12-venv     # основной .venv
sudo apt install python3.11 python3.11-venv     # venv-tts + два из четырёх vendor/*/venv
sudo apt install nvidia-cuda-toolkit             # nvcc, для CUDA-расширений Hunyuan3D-2GP
sudo snap install blender --classic              # ВАЖНО: официальная сборка, не apt —
                                                   # у apt-пакета Blender сломан Cycles bake
                                                   # для skinned mesh (см. 3dtodo.md)
curl -LsSf https://astral.sh/uv/install.sh | sh  # для Animato (Python 3.13 + свой bpy)

# Автопереключение OLLAMA_KV_CACHE_TYPE (f16 для gpt-oss:20b, q8_0 для
# остальных — см. mcp_agent/ollama_kv_cache.py) — узкое NOPASSWD-правило
# ТОЛЬКО на этот один скрипт с этими двумя аргументами, не на sudo вообще:
echo "$(whoami) ALL=(root) NOPASSWD: $(pwd)/scripts/ollama_kv_cache_switch.sh f16
$(whoami) ALL=(root) NOPASSWD: $(pwd)/scripts/ollama_kv_cache_switch.sh q8_0" \
  | sudo tee /etc/sudoers.d/flowai-ollama-kv-cache > /dev/null
sudo chmod 440 /etc/sudoers.d/flowai-ollama-kv-cache
sudo visudo -c   # проверка синтаксиса перед тем, как это правило начнёт действовать

# Ставит всё (main .venv, image-gen, whisper, tts, hunyuan3d-2gp, unirig, animato, supermat, expert-streaming):
python3 setup.py
# Проверить, что скрипт возьмётся делать, без единой реальной команды:
python3 setup.py --dry-run
# Поставить только один компонент:
python3 setup.py --only tts   # main | image-gen | whisper | tts | hunyuan3d-2gp | unirig | animato | supermat | expert-streaming
```

Дальше запускать через лончер `./flowai` (сам находит `.venv`, активировать вручную не нужно) или `python3 cli.py` после `source .venv/bin/activate`.

Компоненты по отдельности:

| `--only` | Что ставит | Нужно для |
|---|---|---|
| `main` | Основной `.venv` + `requirements.txt` + `.env` из `.env.example` | Базового чата — обязателен, всё остальное опционально и от него зависит |
| `image-gen` | `diffusers`/`torch`/`transformers`/`accelerate` в основной `.venv` (нужна GPU) | `generate_image`/`edit_image` — модель (~4-7 GB) качается сама при первом вызове |
| `whisper` | `faster-whisper` в основной `.venv` (CPU) | Голосовой ввод (`Alt+R`) — модель (по умолчанию `medium`, ~1.5 GB) качается сама, размер настраивается в `/settings` |
| `tts` | Отдельный `venv-tts` (Python 3.11) — Chatterbox + расстановка ударений для русского | Голосовой ответ — модель (~2 GB, лицензия Coqui CPML, некоммерческая) качается сама. Все выходные аудиофайлы несут неслышимый цифровой водяной знак (`perth`, офлайн, но не отключается через публичный API) |
| `hunyuan3d-2gp` / `unirig` / `animato` / `supermat` | Каждый — свой `vendor/*/venv` | `/gen_model`, `/anim`, `/gen_texture` (нужна GPU) — веса (Hunyuan3D ~несколько GB, UniRig ~несколько сотен MB, оба на HuggingFace) качаются сами при первом вызове |
| `expert-streaming` | Свой форк `llama.cpp` (см. «Модели» ниже), собственный `venv-build-tools` для cmake/ninja, компилируется из исходников (CUDA) — ставится автоматически и при обычном `python3 setup.py` (без `--only`) | Backend для дефолтной chat-модели `glm-4.7-flash:q4_K_M` (обязателен для неё) — dynamic MoE expert-caching, также экспериментально доступен для `gpt-oss:20b`/`qwen3-coder:30b` (тумблер в `/settings`) — см. `expert_streaming.py` |

Генерация музыки (`generate_music`, `facebook/musicgen-small`, ~2 GB) отдельного шага не требует — использует `transformers`, уже поставленный вместе с `image-gen`. Модель качается сама при первом вызове.

### Скачать модели через Ollama

```bash
ollama pull glm-4.7-flash:q4_K_M   # основной чат — дефолт из коробки (или другая, см. таблицу моделей ниже)
ollama pull qwen2.5vl:7b           # vision — анализ изображений
```

Дефолтная модель чата требует `expert_streaming_enabled=ВКЛ` (тоже дефолт) — обычный `python3 setup.py` (без `--only`) уже собирает нужный форк `llama.cpp` сам (см. «Модели» ниже), веса же качаются отдельно, тем же `ollama pull` выше — сборка бинарника их не скачивает.

Модель переключается на лету через `/settings` внутри чата — там сразу видно, что уже скачано и сколько это весит. Правка `chat_model`/`expert_streaming_enabled` в `settings.py` меняет дефолт только для НОВОЙ установки (без своей `flowai.db`) — на уже существующей БД `/settings` единственный способ сменить модель, `.env`/`OLLAMA_MODEL` больше не используется (см. `CLAUDE.md` → «Models»).

### WSL2: аудио-мост

STT/TTS на WSL2 идут через `powershell.exe` (запись — MCI, воспроизведение — `System.Media.SoundPlayer`), а не через ALSA/PulseAudio — их тут обычно нет и нет прав поставить (`sudo apt install alsa-utils` требует пароль). Для записи с микрофона один раз нужно разрешить это в Windows: **Параметры → Конфиденциальность и защита → Микрофон → «Разрешить классическим приложениям доступ к микрофону»**.

## Модели

### Текстовые (chat + tool use)

**`glm-4.7-flash:q4_K_M`** (дефолт из коробки, `settings.py`) — требует
`expert_streaming_enabled=ВКЛ` (тоже дефолт): собственный `llama-server`-форк
с настоящим dynamic MoE expert-кэшем вместо статичного CPU/GPU сплита
Ollama, см. `expert_streaming.py` — обычный Ollama-путь для ЭТОЙ модели не
годится вообще, архитектура `glm4moelite` в нём не поддерживается без
патча этого форка. Полный `python3 setup.py` (без `--only`) собирает нужный
бинарник автоматически, сама модель качается отдельно, обычным
`ollama pull glm-4.7-flash:q4_K_M` (см. «Установка» выше) — если бинарник
почему-то не собран, flowAI тихо откатывается на обычный Ollama-путь под
ДРУГУЮ модель, а не падает. На expert-streaming загрузка и корректная
остановка генерации для этой модели подтверждены живым тестом — см.
`expert_streaming.py`, раздел «GLM-4.7-Flash».

Два разумных варианта на обычном Ollama-пути (без сборки форка — только
разовый sudoers-шаг выше для автопереключения KV cache), если
`expert_streaming_enabled` выключен:

- **`qwen3-coder:30b`** — лучшее качество из всего, что реально тянется
  локально на обычном Ollama-пути, agentic-кодинг и тул-коллы нативно
  заточены под агента, но ощутимо дольше отрабатывает ответ на
  CPU-инференсе.
- **`gpt-oss:20b`** — заметно быстрее (13 GB суммарного веса против 18-19 GB
  у `qwen3-coder:30b`). Раньше падал на обычном Ollama-пути
  (`OLLAMA_KV_CACHE_TYPE=q8_0`, GGML_ASSERT, известный баг Ollama
  [#16946](https://github.com/ollama/ollama/issues/16946)) — живым
  journalctl-трейсом подтверждено, что причина именно в этой переменной
  (та же модель, тот же прогон, под `f16` отработала несколько ходов
  подряд без единой ошибки), не в самой модели. flowAI автоматически
  переключает `OLLAMA_KV_CACHE_TYPE` под нужную модель перед каждой
  сборкой (`mcp_agent/ollama_kv_cache.py`) — при настроенном sudoers-правиле
  из «Установка» выше это больше не требует ручных действий.

`expert_streaming_enabled` потенциально ещё быстрее и для `gpt-oss:20b`, но
для НЕЁ (не для glm-4.7-flash) это НЕ рекомендуется для реальной работы:
живыми прогонами подтверждены две проблемы парсинга harmony-формата в этом
форке: (1) канал-разметка (`<|channel|>...<|message|>`) иногда ломается, и
рассуждения модели вместе со служебными токенами утекают в видимый ответ
вместо чистого текста; (2) тул-коллы иногда не долетают до настоящего
вызова инструмента вообще — модель пишет вызов прямо в тексте (в чужом, не
соответствующем реальной схеме формате), не через harmony-канал
`commentary to=functions.*`. Обычный Ollama-путь для gpt-oss:20b (см. выше)
не имеет этих проблем — родной harmony/тул-коллинг у самого Ollama гораздо
зрелее, чем у этого экспериментального форка.

Ориентир по железу, на котором эти модели настраивались и тестировались:
ноутбук с **NVIDIA RTX 4050 Laptop (6 GB VRAM)**, 16-ядерный CPU, 32 GB RAM
(на WSL2 под саму WSL из них выделено 24 GB через `.wslconfig` — реальный
объём на железе больше).
На таком железе `qwen3-coder:30b` (MoE, ~3.3B активных параметров из 30B) не
влезает в VRAM целиком и работает в основном на CPU (`ollama ps` показывает
~79%/21% CPU/GPU) — заметно медленнее полностью GPU-резидентной модели, но
ощутимо умнее в агентных задачах и тул-коллах, чем что-либо, что влезло бы в
6 GB видеопамяти целиком.

На железе такого класса (или слабее) **дальше эти модели уже не тянут** — то
есть на 14B моделях выбор становится ХУЖЕ, а не промежуточным: 14B (`qwen3:14b`,
`qwen2.5:14b`, ~9 GB) не помещаются в 6 GB VRAM целиком точно так же, как и
20-30B, но при этом не настолько компактны, чтобы выиграть в скорости — практика
показала, что осмысленных вариантов ровно два, без середины:
- **`glm-4.7-flash:q4_K_M`/`gpt-oss:20b`/`qwen3-coder:30b`**, если важнее
  качество агентных ответов и не жалко ждать (генерация на CPU-инференсе
  может занимать несколько минут на объёмный ответ/файл);
- **модель 7-8B** (`qwen3:8b` / `qwen3.5:9b`), если важнее скорость и полное
  размещение на GPU, ценой заметно более слабого агентного поведения.

| Модель | Размер | Когда использовать |
|---|---|---|
| `glm-4.7-flash:q4_K_M` | 17.7 GB (MoE, ~3B активных) | **Дефолт из коробки.** Требует `expert_streaming_enabled=ВКЛ` (тоже дефолт) — обычный Ollama-путь не поддерживает архитектуру `glm4moelite` в этом форке без патча; на expert-streaming загрузка и корректная остановка генерации подтверждены живым тестом, см. `expert_streaming.py` |
| `gpt-oss:20b` | 13 GB (MoE, ~3.6B активных) | Быстрее qwen3-coder:30b — работает и на обычном Ollama-пути (KV cache переключается автоматически, см. выше) |
| `qwen3-coder:30b` | 18 GB (MoE, ~3.3B активных) | Лучший вариант на обычном Ollama-пути (`expert_streaming_enabled` выкл) — agentic-кодинг, тул-коллы заточены под агента |
| `qwen3:14b` | 9.3 GB | Глубокий reasoning — на 6 GB VRAM хуже обоих соседних вариантов, см. выше |
| `qwen2.5:14b` | 9 GB | Стабильный универсал — та же оговорка про 6 GB VRAM |
| `qwen3.5:9b` / `qwen3:8b` | 5-6 GB | Быстрее, для менее тяжёлых задач — второй разумный вариант на ограниченном железе |
| `qwen3:4b` / `qwen2.5:3b` | 2-2.5 GB | Самые лёгкие, для слабого железа |
| `dolphin3` | 4.9 GB | Альтернативная универсальная модель |

Полный список с описаниями — прямо в `/settings` → «модель».

### Vision (анализ изображений — `analyze_image`)

| Модель | Размер | Качество |
|---|---|---|
| `qwen2.5vl:7b` | ~5 GB | Лучший OCR/анализ (рекомендуется) |
| `qwen2.5vl:32b` | ~18 GB | Мощнее, если хватает VRAM |
| `llava:13b` | 8 GB | Проверенный, дефолт по коду |

Работает через отдельную модель, а не основную chat-модель — они не должны совпадать, ни `glm-4.7-flash:q4_K_M` (дефолт), ни `qwen3-coder:30b` картинки не понимают вообще.

### Генерация/редактирование изображений (`generate_image`/`edit_image`, нужна GPU)

Переключение — `/settings` → «imggen модель».

| Модель | VRAM | Шаги | Качество |
|---|---|---|---|
| `stabilityai/sdxl-turbo` | ~4 GB | 4 | Очень быстрый |
| `ByteDance/SDXL-Lightning` | ~6 GB | 4 или 8 | Быстрый + лучше turbo (рекомендуется для 6 GB VRAM) |
| `stabilityai/stable-diffusion-xl-base-1.0` | ~7 GB | 20-50 | Высокое качество, медленно |
| `stabilityai/stable-diffusion-2-1` | ~4 GB | 20-50 | Хорошее качество |
| `runwayml/stable-diffusion-v1-5` | ~3 GB | 20-50 | Лёгкая классика |

`edit_image` переиспользует уже загруженный pipeline (без передокачки весов) — просто конвертирует его в img2img-режим на лету.

### Распознавание речи (`Alt+R`, faster-whisper)

Переключение — `/settings` → «распознавание речи».

| Модель | Скорость | Точность |
|---|---|---|
| `tiny` | Самая быстрая | Ниже |
| `base` | Быстро | Базовая |
| `small` | Баланс | — |
| `medium` | Медленнее (дефолт) | Точнее |
| `large-v3` | Медленно на CPU | Максимальная |

### Голосовой ответ (Chatterbox, отдельный `venv-tts`)

Фиксированная модель (`ResembleAI/chatterbox` multilingual), не переключается через `/settings` — русский официально в числе поддерживаемых языков. `~4-5x` реального времени на CPU (i7-13620H) — для 10-секундного ответа жди ~45 секунд.

### Генерация музыки (MusicGen)

Фиксированная модель (`facebook/musicgen-small`). Только инструментал — **без вокала**: если попросить «спеть» текст, модель его проигнорирует и просто сгенерирует музыку по стилю. Для настоящих звуковых эффектов (не музыки) эта модель не приспособлена — годится максимум для эмбиента вроде «шум дождя».

### Генерация 3D-моделей (`gen3d/`, все замеры — на 6 GB VRAM)

Настройки — `/settings` → «gen_model ...». Цифры ниже — реальные измерения из
`3dtodo.md`, не оценки.

| Этап | VRAM | Время | Настройка |
|---|---|---|---|
| Генерация меша+текстуры (Hunyuan3D-2GP, профиль 4) | ~2.2 GB | ~7 мин | `gen_model профиль` |
| Multi-view генерация (Hunyuan3D-2mv, `--front/--left/--back/--right`) — ОДНА модель из нескольких ракурсов | ~2.4 GB (замер по `nvidia-smi` во время прогона, не точный peak) | ~14.5 мин (весь `/gen_model`, включая ретопологию+перезапекание) | `--front`/`--left`/`--back`/`--right` |
| Ретопология + перезапекание текстуры: альбедо+normal+AO, плюс плоские roughness/metallic (Blender, CPU) | — | секунды (три бейк-прохода — см. `rebake_texture.py`) | `gen_model полигонаж` (дефолт 15000) |
| AI-оценка roughness/metallic (SuperMat: рендер 6 ракурсов + инференс + проекция на UV) | своя SD2.1-модель, отдельный подпроцесс | ~6-8 мин | `gen_model AI PBR` (дефолт ВКЛ, нужен `vendor/supermat`) |
| LOD (на каждый уровень `--lod N`): ретопология+перезапекание из сырого меша | — | как строка выше × N | `--lod N` |
| Риг — скелет (UniRig) | ~4.0 GB | ~1 мин | — |
| Риг — скиннинг, Automatic Weights (Blender, CPU, дефолт) | — | секунды | `gen_model скиннинг` |
| Риг — скиннинг, UniRig skin-модель (точнее, впритык) | ~5.87 GB | ~1-2 мин | `gen_model скиннинг` |
| Анимация (Animato + текущая chat-модель) | зависит от chat-модели | ~1-2 мин | — |

Профиль offload 3 (вместо дефолтного 4) даёт ~3% скорости за счёт почти
вдвое большего пика VRAM (2.2→4.34 GB) — не рекомендуется на 6 GB карте.

## Голосовой режим

### Голосовой ввод — `Alt+R`

Жмёшь `Alt+R` (или `Alt+К` в русской раскладке) → запись N секунд (настраивается, `/settings` → «секунд записи», дефолт 6) → распознанный текст сам подставляется в поле ввода. Ничего не отправляется автоматически — можно поправить перед Enter.

### Голосовой ответ — тумблер `/settings` → «голосовой режим»

Когда включён:
- каждый финальный ответ агента озвучивается вслух (Chatterbox);
- `chat_model` автоматически переключается на **более быструю** модель (`/settings` → «модель голос. режима», дефолт `qwen3:8b`) — основная chat-модель (`glm-4.7-flash:q4_K_M` по умолчанию, или `qwen3-coder:30b`) слишком тяжёлая и заточена под кодинг, а не разговор;
- при выключении голосового режима возвращается та модель, что была выбрана до включения.

Список моделей для голосового режима в `/settings` намеренно ограничен быстрыми универсальными моделями (не coder/reasoning-теги) — здесь важна скорость ответа, а не глубина.

### Ограничения

- Синтез речи — не в реальном времени (см. таблицу моделей выше), это ок для «спросил и подождал», но не для живого разговора без пауз.
- Постоянно слушающего режима с активационным словом («привет, Флоу») пока нет — WSL2 не даёт живого аудио-потока (мост только «запиши N секунд → файл»), реализация такого режима означала бы фоновый поллинг короткими чанками через Whisper, а не настоящий wake-word движок.

## Запуск

### Консольный чат

```bash
./flowai
# или
python3 cli.py
```

Команды в чате: `/img путь.jpg`, `/paste`, `/gen промпт`, `/gen_model промпт [--rig]`, `/anim описание движения`, `/gen_texture @модель @картинка`, `/usage`, `/settings`, `/clear`, `/help`.

### Запуск из любой директории (Linux)

**Рекомендуемый способ** — `pyproject.toml` (охватывает базовый чат: `cli.py` + всё, что перечислено в `requirements.txt`; тяжёлые опциональные части — image-gen/whisper/tts/`/gen_model`-пайплайн — по-прежнему ставятся отдельно через `python3 setup.py --only ...`, см. выше, в СВОИ venv, а не через этот пакет):

```bash
source .venv/bin/activate
pip install -e .
```

Даёт настоящую команду `flowai` в `.venv/bin/` — работает из любой директории, пока `.venv` активирован (repo_path берётся из директории, откуда вызвали, а не из каталога установки flowAI). Если venv не активирован каждый раз вручную — засимлинковать сам исполняемый файл в директорию из `$PATH`:

```bash
mkdir -p ~/.local/bin
ln -s "$(pwd)/.venv/bin/flowai" ~/.local/bin/flowai
```

**Более лёгкая альтернатива без `pip install`** — тот же трюк, но с лончер-скриптом `./flowai` (сам находит `.venv` по своему реальному расположению через `readlink -f`, активировать ничего не нужно):

```bash
mkdir -p ~/.local/bin
ln -s "$(pwd)/flowai" ~/.local/bin/flowai
```

В обоих случаях, если `~/.local/bin` ещё не в `$PATH` — добавить в `~/.bashrc`/`~/.zshrc`:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

После этого достаточно открыть терминал в нужном проекте и вызвать просто `flowai`.

### HTTP-сервер

```bash
uvicorn main:app --reload
```

Сервер на `http://localhost:8000`, `POST /chat` со стримингом через SSE.

## Генерация 3D-моделей

Требует установки — см. «Установка» → «Генерация/анимация 3D-моделей» выше.
Полная история пайплайна (что пробовали, что не сработало и почему, все
измерения VRAM) — `3dtodo.md`.

### В CLI

```
You: /gen_model a cute penguin holding a sign
You: /gen_model [Image-1] --rig
You: /gen_model @penguin --rig            (картинка из img-refs/penguin.png)
You: /gen_model @a.png @b.png @c.png       (батч — 3 отдельные модели, не одна с трёх ракурсов)
You: /gen_model a cute penguin --raw       (без ретопологии — сырой меш Hunyuan3D как есть)
You: /gen_model a cute penguin --lod 3     (+ 3 доп. модели пониже полигонажем: _lod1, _lod2, _lod3)
You: /anim wave with the right arm
You: /anim @penguin wave with the right arm   (конкретная модель, не последняя)
You: /gen_texture @penguin @new_skin.png       (перекрасить готовую модель по референсу)
You: /gen_texture @new_skin.png @penguin       (порядок аргументов не важен)
```

`/gen_model` принимает текстовый промпт (сначала уйдёт в `generate_image`,
результат — на вход image-to-3D), `[Image-N]`/путь к готовой картинке, или
`@имя` — файл из `img-refs/` (без расширения тоже работает, автокомплит по
`@` всплывает сразу после `/gen_model `/`/anim `, как у слэш-команд). Несколько
`@ref` подряд — **батч**: каждая картинка даёт свою отдельную модель, друг за
другом (Hunyuan3D-2mini не умеет собирать одну модель точнее из нескольких
ракурсов — список картинок в его API просто гоняется как независимый батч,
см. `3dtodo.md`).

Чтобы вместо батча получить **одну** модель из нескольких ракурсов — отдельные
флаги `--front @имя --left @имя --back @имя --right @имя` (Hunyuan3D-2mv,
другой чекпоинт: см. `3dtodo.md`, реально сплавляет ракурсы в одно условие
генерации, а не гоняет их батчем). Ракурсы фиксированные, не произвольные:
`front` — прямо на объект (0°), `left` — поворот на 90° влево, `back` — со
стороны спины (180°), `right` — поворот на 90° вправо (конвенция самой
модели). Нужен минимум `front`, для реального эффекта — `front`+`left`+`back`
(так делают собственные примеры vendor'а Hunyuan3D-2GP; `right` почти не
используется). Скачивает свой чекпоинт (~9.2 GB) при первом использовании;
полный `/gen_model` в этом режиме — ~14.5 мин на 6 GB карте (см. таблицу выше).
Каждое из `--front`/`--left`/`--back`/`--right` — только существующий файл
(`@имя`/путь/`[Image-N]`), без генерации по текстовому промпту.

Флаги: `--rig` добавляет скелет+скиннинг (без флага — просто текстурированный
меш, быстрее). `--raw` пропускает ретопологию/перезапекание текстуры целиком —
отдаёт сырой меш Hunyuan3D как есть (сотни тысяч граней, не для игры — только
посмотреть на исходное качество генерации). Комбинируются: `--raw --rig`
формально работает, но не проверялось на таком плотном меше — риск, что
просто будет намного дольше, а не что-то сломается (UniRig сам делает
внутренний ресемплинг на этапе extract).

`Ctrl+C` во время `/gen_model`/`/gen_texture` реально убивает текущий дочерний
процесс (Blender/Hunyuan3D-2GP/UniRig/SuperMat), а не просто отменяет ожидание
— раньше подпроцесс молча доигрывал до конца в фоне даже после отмены (см.
`3dtodo.md` про этот баг и про сопутствующий deadlock, который заодно нашли и
починили).

Ретопология+перезапекание (полный пайплайн, без `--raw`) теперь пекут **альбедо,
normal map И AO** (Cycles bake, selected-to-active, `gen3d/blender_scripts/rebake_texture.py`)
— неровности/детали геометрии, которые срезает Decimate, возвращаются в виде
normal- и AO-текстур на итоговый низкополигональный меш, а не теряются насовсем.
Roughness/metallic по умолчанию (без AI PBR — плоские константы, у Hunyuan3D-2GP
нет своей оценки материала) заменяются на настоящий `metallicRoughnessTexture`,
оценённый **SuperMat**: `gen_model AI PBR` (`/settings`, **дефолт ВКЛ**) —
рендер модели с 6 ракурсов под студийным светом → per-view оценка
roughness/metallic → обратная проекция на реальный UV меша, без raycast-проверки
видимости (известное ограничение: на самозаслоняющих формах возможен лёгкий шов
между ракурсами). Отдельный подпроцесс со своей SD2.1-моделью — добавляет
~6-8 минут к `/gen_model` и требует `vendor/supermat`
(`python3 setup.py --only supermat`, ставится автоматически при обычном
`python3 setup.py`) — на инсталляциях без него `/gen_model` без `--raw` будет
падать понятной ошибкой на этом шаге, пока supermat не поставлен или AI PBR не
выключен обратно в `/settings`.

`--lod N` — сгенерировать ещё N моделей пониже полигонажем, **отдельными
файлами** (не несколько LOD в одном .glb — расширение glTF для этого,
`MSFT_lod`, не поддерживается ни Blender-экспортёром, ни `trimesh`, а раздельные
файлы — это ровно то, что ждут LOD-группы игровых движков). Названы
`{модель}_lod1.glb` .. `{модель}_lodN.glb`, основная модель остаётся
`{модель}.glb` (LOD0, полное качество). Каждый LOD ретопологизируется и
перепекается (альбедо+normal) заново **из исходного сырого меша Hunyuan3D**, а
не из предыдущего LOD — чтобы потеря детализации не накапливалась по цепочке;
целевой полигонаж каждого уровня — половина предыдущего. Риг **не** дублируется
на LOD-модели — они всегда без скелета, даже если основная модель с `--rig`
(общий скелет на мешах разной топологии требует отдельного шага переноса
скиннинга, которого в этом пайплайне нет). AI PBR тоже не повторяется на
LOD — сам по себе добавляет ~6-8 минут, на каждый LOD-уровень это свело бы на
нет их смысл (быстрые, менее детальные варианты).

`/anim` без `@имя` анимирует **последнюю сгенерированную в этой сессии**
модель (должна быть с ригом) — `@имя` берёт конкретную из `generated/models/`
вместо последней.

Результат — `.glb` в `generated/models/`.

`/gen_texture` перекрашивает **уже готовый** меш новой текстурой по картинке-
референсу, не трогая геометрию — пропускает генерацию формы (`Hunyuan3D-2mini`)
целиком и гоняет только `Hunyuan3D-Paint`, поэтому в разы быстрее полного
`/gen_model` (~5-6 мин против ~7-8). Два аргумента, `@модель` и `@картинка`, —
**в любом порядке**: команда сама определяет, что есть что, по тому, в каком
каталоге находится файл (`generated/models/*.glb` — модель, `img-refs/*` —
картинка), а для голых путей — по расширению. Работает на любом меше, который
понимает `trimesh` (`.glb`/`.gltf`/`.fbx`/`.obj`), не только сгенерированном
самим `/gen_model`. UV-развёртка перестраивается с нуля (`xatlas`) — прежняя
не сохраняется.

Отключить весь пайплайн (если не установлен/не нужен) — `/settings` →
«gen_model включён».

**Надёжность `/anim`**: скрипт анимации пишет LLM (текущая chat-модель) —
если она подставит несуществующее имя кости (типичная галлюцинация —
generic/Mixamo-имена вроде `RightArm` вместо реальных `bone_N` этого рига),
`animate_3d_model` автоматически отдаёт ей ошибку и просит исправиться
(до 2 повторных попыток). Механизм коррекции рабочий (сообщение об ошибке
меняет её следующую догадку), но 100% успеха не гарантирует — это зависит от
того, насколько выбранная модель точно следует контексту, а не более
привычным именам костей. Если анимация не получилась — попробуй другое
описание движения, или более крупную/аккуратную модель через `/settings`.

### Через агента (обычным текстом)

```
You: сгенерируй 3D-модель дракона с ригом и заставь его махать крылом
```

Агент сам вызывает `generate_3d_model`/`animate_3d_model`/
`generate_texture_for_model` (MCP-тулы, `mcp_agent/servers/gen_model_server.py`)
— все три в `TOOLS_REQUIRING_APPROVAL`, подтверждение спросится перед запуском

## Как это работает

```
cli.py / main.py (HTTP)
        │
        ▼
pipeline_mode=ВКЛ (дефолт)             pipeline_mode=ВЫКЛ (легаси)
        │                                       │
        ▼                                       ▼
mcp_agent/pipeline.py — Router →       mcp_agent/agent.py — stream_chat():
Analyzer → Planner → Coder →           монолитный self-heal цикл,
Verifier (mcp_agent/router.py,         семантическая проверка, ретраи
roles.py, stage_runner.py — своя               │
retry-механика на каждую стадию)               │
        │                                       │
        └───────────────────┬───────────────────┘
                             ▼
mcp_agent/agent_builder.py — собирает LangGraph-агента/роль: модель
        │                     (Ollama или expert-streaming, см. «Модели»)
        │                     + тулы из MCP-серверов
        ▼
mcp_agent/servers/*.py — каждый тул-домен свой MCP-сервер (подпроцесс):
                          bash_exec, git_extra, fs_extra, code_search,
                          web_search, memory, knowledge, rag,
                          image_gen (generate_image/edit_image),
                          vision (analyze_image), music (generate_music),
                          gen_model (generate_3d_model/animate_3d_model)
                          + официальные filesystem/git/fetch MCP-серверы
        │
        ▼ (gen_model — единственный, кто дальше шеллится ещё глубже)
gen3d/pipeline.py — subprocess-вызовы в vendor/{hunyuan3d-2gp,unirig}/venv
                     (несовместимые torch/CUDA-сборки, свои от flowAI) +
                     систему Blender + gen3d/animato_client.py (персистентный
                     `uv run fastapi` подпроцесс vendor/animato)
```

MCP-серверы кешируются на весь процесс (дорого поднимать заново на каждый ход), а сама модель пересобирается на лету при смене `chat_model` через `/settings` (например, при включении голосового режима) — без перезапуска подпроцессов.

```
Alt+R → ui/audio.py:record_from_mic (PowerShell/MCI) → transcribe (faster-whisper)
      → текст в поле ввода → обычный ход агента → готовый ответ
      → (если voice_mode) ui/audio.py:speak → venv-tts subprocess (Chatterbox)
      → play_wav (PowerShell/SoundPlayer)
```

## Добавить инструмент

Каждый домен инструментов — свой MCP-сервер в `mcp_agent/servers/`. Например, `mcp_agent/servers/music_server.py`:

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("my_tool")

@mcp.tool()
async def my_tool(arg: str) -> str:
    """Описание для модели — ТОЛЬКО на английском (см. CLAUDE.md)."""
    return f"result for {arg}"

if __name__ == "__main__":
    mcp.run()
```

Зарегистрировать в `mcp_agent/config.py` (`raw_servers` dict) — по умолчанию сервер запускается тем же интерпретатором, что и сам flowAI, но можно указать любой другой (так сделано для `venv-tts` — см. `ui/audio.py`, где TTS вызывается subprocess'ом вручную, а не через MCP, именно из-за разных venv). Если тул мутирует состояние (пишет файлы, тратит ощутимое время/ресурсы) — добавить его имя в `TOOLS_REQUIRING_APPROVAL` там же.

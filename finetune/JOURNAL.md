# Журнал дообучения — 2026-08-08

Один день работы над LoRA-дообучением flowAI на реальной истории
использования (`~/.local/share/flowai/flowai.db`). Ниже — что сделано, что
выяснено и в каком состоянии всё осталось.

## 1. Точный tool_scope по роли

Раньше каждому обучающему примеру давался ЛИБО весь реестр тулов (37 штук,
~1876 токенов сам по себе — на 6 ГБ карте это оставляло слишком мало места
на историю диалога), либо случайное подмножество (`_tools_subset`) —
приближение.

Добавили точный путь: `episodic_messages` содержит роль `stage_changed` с
именем текущей роли пайплайна (`analyzer`/`planner`/`quick_fix`/`coder`/
`verifier`/`casual`). Для этих сессий `extract_dataset.py` теперь берёт
РЕАЛЬНЫЙ набор тулов роли прямо из `mcp_agent/roles.py`
(`investigator_tools`, `planner_tools`, `executor_tools`, `coder_tools`,
`verifier_tools`) и кладёт его в поле `tool_scope` каждого примера. Если
вызванный тул не входит в набор роли — считаем разметку противоречивой и
откатываемся на `None` (легаси-путь со случайной подвыборкой).

Итог по всему датасету (1693 примера после фильтрации отклонённых): **717
с точным tool_scope, 976 легаси** (без разметки роли — старые сессии без
`stage_changed`).

`finetune_cli.py:cmd_train` использует точный `tool_scope`, когда он есть, и
`_tools_subset` только как запасной вариант.

## 2. Почему память росла с длиной контекста — и как это обойти

При обучении `logits = model(x).logits` считает логиты по ВСЕМУ словарю
(151936 токенов у Qwen2.5) для КАЖДОЙ позиции последовательности — тензор
`длина × vocab_size`, который растёт линейно с длиной и на 2000-3000
токенах весит гигабайты сам по себе (плюс внутренние буферы cross-entropy
типа log-softmax, которые множат это в несколько раз).

Ключевое наблюдение: loss в этом пайплайне считается только на
`target_tool_call` — а это всегда ХВОСТ последовательности (см.
`_render_raw`: `full_text = prefix + целевой_вызов`, без
`add_generation_prompt` после него). Значит, весь остальной текст в лоссе
не участвует, и не нужно прогонять его через словарную проекцию.

Подключили параметр `logits_to_keep` у `Qwen2ForCausalLM.forward` — он
считает логиты только по последним k позициям (`slice(-logits_to_keep,
None)` внутри HF-реализации). `k` берём как `mask.sum()` — количество
токенов с loss_mask=1, которые по построению лежат подряд в конце.

Замер на реальной карте (6 ГБ, LoRA только на `q_proj`/`v_proj`):

| seq_len | без фикса | с `logits_to_keep=64` |
|---|---|---|
| 1024 | 7.79 сек / 7.15 ГБ | 6.68 сек / 6.08 ГБ |
| 2048 | 38.36 сек / 12.27 ГБ | 37.03 сек / 10.09 ГБ |
| 3072 | 70.13 сек / 17.19 ГБ | 64.79 сек / 13.91 ГБ |
| 4096 | (не проверяли) | 99.56 сек / 17.83 ГБ |
| 6144 | — | OOM |

Экономия растёт с длиной (как и ожидалось — она пропорциональна разнице
`T - k`), но НЕ убирает ограничение целиком: активации самого трансформера
(attention/MLP по всем слоям) всё равно растут с длиной и на 6 ГБ карте
всё равно упираются в потолок уже на ~1500-2000 токенах. Дальнейшее (Flash
Attention память-эффективные ядра, оффлоад слоёв на CPU) — избыточно для
локального LoRA на 6 ГБ карте, не стали делать.

Правка — `finetune_cli.py`, цикл обучения в `cmd_train`: вычисляем `k`,
вызываем `model(x, logits_to_keep=k)`, обрезаем `y`/`mask` до последних `k`
позиций перед `cross_entropy`.

## 3. Почему WSL казался медленнее Windows — и почему нет

(Расследование до сегодняшнего дня, для полноты картины.) Подозревали, что
WSL2 сам по себе замедляет CUDA/bitsandbytes (~60-70 сек/шаг, ~18-20 ГБ на
6 ГБ карте). Параллельный тест на нативном Windows дал ИДЕНТИЧНЫЙ результат
на той же конфигурации — вопрос был не в платформе, а в том, что конфиг
(seq_len=2000, LoRA на всех 7 модулях) объективно требует ~18-20 ГБ. После
уменьшения LoRA до `q_proj`/`v_proj` и seq_len до 512 — обе платформы
показали сравнимую, нормальную скорость. WSL не медленнее Windows при
одинаковой конфигурации.

| max_length | проходит | из них точный tool_scope |
|---|---|---|

## 5. Первый реальный прогон обучения

Конфиг: `Qwen2.5-3B-Instruct` (уже скачана раньше для дистилляции в учебном
проекте — не тянули новую модель), 4-бит QLoRA, `lora_r=16`,
`lora_alpha=32`, `target_modules=q_proj,v_proj`, `max_length=1536`,
`--boost-arg replace_lines:expected_first_line --boost-weight 3` (усиление
веса примеров с указанием точной строки правки — исходная больная тема,
из-за которой всё это затевалось).

619 примеров-повторов (617 уникальных + усиление). Загрузка и токенизация —
секунды. Обучение пошло без единого OOM, ~15-20 сек/шаг, GPU 5.9/6.1 ГБ
(у предела карты, но стабильно). При 619 примерах × 2 эпохи = 1238 шагов
это ~5.5 часов на весь прогон.

**Остановлено пользователем осознанно** («выключай, потом поиграемся») —
не из-за ошибки, а чтобы вернуться позже. Процесс убит (`SIGTERM`), GPU
освобождена, монитор снят.

Важное уточнение, которое обсуждали: часы — это не деградация и не баг,
это просто размер датасета (619) × число шагов, при той же скорости на
шаг, что и в короткие тестовые замеры (которые делали всего 5 шагов и
поэтому казались мгновенными). 5.5 часов на локальный LoRA-файнтюн на 6 ГБ
карте — нормальная величина для этого класса задач, не аномалия.

## 6. Добавлена возможность продолжить обучение по эпохам

Раньше `cmd_train` при каждом запуске инициализировал LoRA-веса заново.
Добавили `--resume-from <путь_к_адаптеру>` — загружает уже сохранённый
адаптер (`PeftModel.from_pretrained(..., is_trainable=True)`) и продолжает
обучение на нём вместо новой инициализации. Это позволяет прогнать 1 эпоху,
посмотреть на результат, и при необходимости продолжить ещё одной эпохой —
БЕЗ повторной инициализации с нуля.

Это не противоречит правилу «не чейнить адаптеры при росте датасета» (см.
README, раздел «Про последовательные дообучения») — то правило о риске
забывания при введении НОВЫХ данных. Здесь тот же самый датасет, просто
больше шагов подряд — риска дрейфа нет, это математически близко к тому,
как если бы сразу запустили побольше эпох.

## 7. Текущее состояние / как продолжить

Обучение НЕ завершено. Чтобы продолжить с нуля на тех же настройках:

```bash
python finetune/finetune_cli.py train \
  --dataset finetune/dataset.jsonl \
  --base-model Qwen/Qwen2.5-3B-Instruct \
  --epochs 1 \
  --lr 2e-4 \
  --lora-r 16 --lora-alpha 32 \
  --lora-target-modules q_proj,v_proj \
  --max-length 1536 \
  --boost-arg replace_lines:expected_first_line --boost-weight 3
```

Затем, если результат первой эпохи понравится, продолжить второй:

```bash
python finetune/finetune_cli.py train \
  --dataset finetune/dataset.jsonl \
  --base-model Qwen/Qwen2.5-3B-Instruct \
  --epochs 1 \
  --resume-from finetune/lora_adapter \
  --lr 2e-4 --max-length 1536 \
  --boost-arg replace_lines:expected_first_line --boost-weight 3
```

(`--adapter-out` по умолчанию — `finetune/lora_adapter`, туда же и
сохраняет; `--resume-from` должен указывать на тот же путь, чтобы
продолжить именно тот адаптер.)

Дальше по плану — `merge`/`gguf`/`install`, чтобы вернуть дотюненную модель
в Ollama. `llama-quantize` уже собран (`~/llama.cpp/build/bin/`) — путь в
`cmd_gguf` при этом шаге нужно будет поправить (сейчас ожидает бинарник
прямо в `llama_cpp_dir`, а не в `build/bin/`).

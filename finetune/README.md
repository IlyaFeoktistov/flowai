# LoRA-дообучение flowAI под свои тулы

Цель: `qwen3-coder:30b` (или любая другая модель flowAI) туго вызывает тулы —
дообучаем её на реальной истории использования, чтобы она делала это надёжнее.

**Статус на сейчас**: `extract` реально протестирован на живой базе (1691
пример после фильтрации отклонённых/непроверенных раундов, с точным
`tool_scope` по роли для 717 из них). `train` реально
запускался на `Qwen2.5-3B-Instruct` (QLoRA, `q_proj`/`v_proj`,
`max_length=1536`) — обучение шло без ошибок, но было сознательно
остановлено на середине первой эпохи, чтобы продолжить позже (см.
подробности и решения дня в [`JOURNAL.md`](./JOURNAL.md)). `merge`/`gguf`/
`install` ещё не прогонялись целиком.

## Откуда берутся данные

`~/.local/share/flowai/flowai.db`, таблица `episodic_messages` — полная,
персистентная история диалогов flowAI (см. `episodic/writer.py`). Внутри
раунда `self_heal_reject` помечает, что система сама отклонила ответ —
такие раунды исключаются из позитивного датасета по умолчанию. Это работает
независимо от настройки `self_heal_enabled` в `/settings` — она выключает
только ретраи, а сама проверка (и её reject-сигнал для датасета) считается
всегда (см. `mcp_agent/agent.py:stream_chat`).

`self_heal_reject` как логируемое событие появился не с первого дня проекта
(добавлен 2026-07-06) — раунды старше этой даты физически не могли получить
reject, даже если бы модель ответила неправильно. `extract_dataset.py`
помечает такие раунды `verified=false` (отличая "не проверялось" от
"проверено и принято") и по умолчанию исключает их из датасета так же, как
отклонённые — иначе вся история до этой даты молча засчиталась бы как
подтверждённо хорошая.

## Шаг 1 — извлечь датасет (уже работает, ничего скачивать не нужно)

```bash
python finetune/finetune_cli.py extract --dataset finetune/dataset.jsonl
```

Пример реального прогона (2026-08-11): 128 сессий → 1896 вызовов тула → 1691
после исключения 34 отклонённых раундов и 171 непроверенных (старше
2026-07-06, см. выше). Каждая строка `dataset.jsonl`:

```json
{"session_id": "...", "seq": 19, "messages": [...история user/assistant/tool...],
 "target_tool_call": {"name": "read_file", "args": {"path": "..."}},
 "rejected": false, "verified": true}
```

`messages` — история ДО целевого вызова, `target_tool_call` — то, что модель
должна научиться воспроизводить (loss считается только на нём — тот же
принцип маскирования, что в `gpt_cli.py --qa-format` из соседнего учебного
проекта).

Частоты тулов в датасете сильно разные (300+ примеров на `read_file_range`,
1 пример на редкие D&D-тулы) — это отражает реальное использование, а не
баг. Редкие тулы дообучение вряд ли заметно улучшит просто по нехватке
примеров.

## Шаг 2 — выбрать и скачать базовую модель (ЕЩЁ НЕ СДЕЛАНО)

`qwen3-coder:30b` из Ollama — это GGUF, для LoRA нужен HF-репозиторий той же
модели отдельно (существенно больше по размеру, чем GGUF-квант). Перед тем
как качать — стоит решить:
- Меньшая модель того же семейства (Qwen2.5-Coder-7B/14B-Instruct) — быстрее
  скачать и обучить, можно сравнить эффект до/после на том же датасете, но
  итоговая модель слабее 30B в основе.
- Сам `qwen3-coder:30b` в HF-формате — соответствует тому, что реально
  используется, но заметно дольше/тяжелее по ресурсам даже с QLoRA.

## Шаг 3 — обучение

```bash
pip install -r finetune/requirements.txt   # отдельно от основных зависимостей flowAI
python finetune/finetune_cli.py train --dataset finetune/dataset.jsonl \
  --base-model Qwen/Qwen2.5-Coder-7B-Instruct --epochs 2
```

QLoRA: базовая модель грузится в 4-бит и замораживается, обучаются только
маленькие LoRA-адаптеры (`--lora-r`/`--lora-alpha`) поверх attention/MLP
слоёв. Loss считается только на токенах `target_tool_call` — вопрос/история
из loss исключены, как и при обычной SFT.

**Известное упрощение**: промпт для обучения собирается через
`tokenizer.apply_chat_template(..., tools=...)` со схемами тулов "имя +
произвольные kwargs" — это НЕ обязательно побайтово совпадает с тем, что
реально видит модель через `langchain_ollama` в проде (у LangChain своё
форматирование). Для поведенческого переноса этого обычно достаточно, но
если результат разочарует — разница форматов промпта первая кандидатура
на разбор.

## Шаг 4 — влить LoRA в веса

```bash
python finetune/finetune_cli.py merge --base-model Qwen/Qwen2.5-Coder-7B-Instruct
```

## Шаг 5 — сконвертировать в GGUF (нужен llama.cpp)

```bash
git clone https://github.com/ggml-org/llama.cpp ~/llama.cpp && cd ~/llama.cpp && make llama-quantize
python finetune/finetune_cli.py gguf --llama-cpp-dir ~/llama.cpp
```

## Шаг 6 — положить обратно в Ollama

```bash
python finetune/finetune_cli.py install --ollama-tag flowai-tuned
ollama run flowai-tuned
```

## Или всё разом

```bash
python finetune/finetune_cli.py all \
  --base-model Qwen/Qwen2.5-Coder-7B-Instruct \
  --llama-cpp-dir ~/llama.cpp \
  --ollama-tag flowai-tuned
```

## Про последовательные дообучения по мере роста данных

Не продолжайте обучение LoRA-адаптера v1 → v2 → v3 цепочкой на только новых
данных — риск дрейфа/забывания старого (тот же эффект, что и в учебном
проекте `~/projects/AI`, где online-learning на новых репликах ломал старые
ответы). Правильный способ: при каждом новом раунде дообучения запускать
`extract` заново на ВСЕЙ накопленной истории (старые + новые сессии) и
обучать LoRA **с нуля** от базовой модели на этом полном датасете — версии
независимы, дрейф не накапливается. Датасет пока маленький — переобучение с
нуля быстрое, время обучения будет расти медленно вместе с объёмом данных,
а не взрывным образом.

## Файлы

| Файл | Что делает |
|---|---|
| `extract_dataset.py` | Извлекает (история → тул-вызов) из `flowai.db`. Протестирован. |
| `finetune_cli.py` | Единая точка входа: `extract`/`train`/`merge`/`gguf`/`install`/`all`. |
| `requirements.txt` | ML-зависимости именно для дообучения (torch/transformers/peft/bitsandbytes) — отдельно от основных зависимостей flowAI. |
| `dataset.jsonl` | Результат `extract` (в `.gitignore`, генерируется заново). |
